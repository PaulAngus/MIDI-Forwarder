# MIDI Forwarder 1.0.5

Windows development builds, 21 October 2026. No public release has been uploaded.

Client and Server now pin all four shared MIDI packages to **0.3.11**. The shared
library includes complete-message Windows MIDI Services sends and recovery from
incomplete incoming SysEx when a MIDI 1.0 input opens during another application's
transfer. The Forwarder's raw UMP relay remains unchanged; this dependency update
does not add Fractal-specific message handling. Application version metadata is
numeric: product version `1.0.5`, file version `1.0.5.0`.

## Local validation

- `dotnet test MIDI-Forwarder.slnx -c Release`: 162 passed (Core 71, Client 50,
  Server 41), no failures or skips.
- `tools/Publish-Windows.ps1 -SigningCertificateThumbprint ''`: both self-contained
  Windows x64 EXEs and ZIP/checksum pairs built successfully. These are unsigned
  development builds.
- `tools/Test-BundledWindowsMidiApi.ps1 -CheckVirtualPorts`: each EXE, copied alone
  into a separate folder with a fresh .NET bundle cache, loaded its bundled API.
  Exactly one public MIDI 1.0 input/output was exposed; Program Change and
  multipart SysEx passed in both directions using temporary test ports.

## Two-computer FM9 test

The development PC (`192.168.2.10`) ran the packaged Client; Windows 11 workstation
`192.168.2.155` ran the packaged Server with the USB-connected FM9, firmware 12.00.
Both used Windows MIDI Services. The workstation's direct FM9-Edit remained
running. A copy of that existing signed FM9-Edit executable also connected through
the Client's public `FM9 Forwarder Test` input and output and loaded the preset,
scene names and grid. This distinct port name avoids another existing development
interface with the default `MIDI Forwarder` name.

Read-only checks used Preset Maestro's production MIDI and scan implementations
with a separate test profile. Requests were restricted to identity, current state,
preset names and stored preset reads; no presets were selected, edited or saved.

- Names-only: 512 slots in 8.045 seconds with the workstation editor running.
- First full scan: 512 slots, Complete, no failed presets, in 218.706 seconds.
  Two 15-second response timeouts (zero-based slots 165 and 229) recovered on
  retry. A 1.5-second name timeout at empty slot 376 fell back to a successful
  stored-preset read. The client-side editor was connected during the closing
  part of this run.
- Final EXEs after restart: names-only read of 512 slots in 8.764 seconds.
  Client-side FM9-Edit reconnected automatically and loaded the preset again.
- Preset Maestro's actual sync command, using an isolated headless window/profile
  with both editors connected: 512 slots, Complete, no failed presets, in 185.334
  seconds. One 15-second stored-preset timeout at slot 252 recovered after the
  scanner's quiet period and retry. No input queue drops were recorded.
- The two full reads agreed on every preset name and scene name and on all
  populated preset content hashes. Empty slot 376 was represented as a decoded
  empty preset in the first run and a name-only empty entry in the second.
- Server stop/restart: the Client reconnected automatically, FM9-Edit was observed
  connected again, and all 512 names were read in 10.985 seconds. A name request
  at slot 265 timed out once and succeeded on retry.

The FM9's active preset and scene were checked before and after successful reads
and remained unchanged. Raw traces and test profiles are private, ignored files
under `artifacts/fm9-0.3.11/`; offline test results are under
`artifacts/tests/midi-0.3.11/`.

The final Client was installed at `C:\bin\MidiForwarder.Client.exe` on the
development PC, and the final Server at `C:\bin\MidiForwarder.Server.exe` on
the workstation, retaining backups of the previous executables. The temporary
server and client connection were stopped after testing; the workstation's
existing FM9-Edit process was left running.

The recovered timeouts mean this is not evidence of a timeout-free full scan.
In each long stored-preset timeout, other incoming traffic continued and the FM9
sent result codes `0x03:0x01` followed by `0x03:0x00`, without the requested dump
frames. This establishes missing dump replies while the connection was alive;
the cause of that remaining pause is not established by these tests. The shared
complete-MIDI-message send fix does not batch the Forwarder's raw UMP send path.
These tests do not qualify a clean Windows installation, Windows 10, macOS, MIDI 2.0
hardware, or preset-write operations.
