# MIDI Forwarder 1.0.6

Windows development builds, 21 October 2026. Shared MIDI packages: **0.3.12**.
No public release has been uploaded.

## Missed FM9 replies with FM9-Edit running

The Windows server previously submitted each forwarded SysEx7 UMP fragment
separately. A request could therefore start on the physical endpoint, wait for
its next TCP fragment, and be interrupted by another application's message.
The complete-MIDI-message batching in helper 0.3.11 did not cover this raw UMP
path. Missing replies made Preset Maestro wait for its response timeout and
retry, even while other MIDI traffic continued.

Helper 0.3.12 collects each outgoing raw SysEx7 message before submitting it to
the physical endpoint. Short requests now use one native transfer. Groups and
all original UMP words are preserved, other packet types pass through unchanged,
and buffered memory is bounded. Large messages split only at complete UMP
boundaries when required by the endpoint's advertised transfer limit. This adds
no Fractal-specific handling, forwarding protocol change or deliberate delay.
Both Forwarder packages pin the new helper; their numeric product version is
`1.0.6` and file version `1.0.6.0`.

This does not implement global stream ownership between unrelated applications;
Microsoft tracks that separately in [Windows MIDI Services issue 60](https://github.com/microsoft/MIDI/issues/60).

## Regression and packaging checks

- Before the fix, `MidiCheck --self-test --raw-ump` failed with an out-of-sequence
  SysEx7 packet while concurrent raw UMP and legacy writers used a temporary
  Windows endpoint. After the fix, three runs passed with every expected message
  intact and no duplicates. The complete-MIDI-message self-test also passed.
- Shared library: 82 offline tests passed, including eight new cases covering
  exact word/group preservation, independent groups, realtime/MIDI 2.0
  pass-through, native transfer boundaries, memory limits, malformed packets and
  abandoned messages.
- Forwarder solution: all 162 tests passed (Core 71, Client 50, Server 41).
- Both Windows x64 EXEs and ZIP/checksum pairs were produced with the normal
  local publisher. These are unsigned development builds.
- Standalone dependency verification passed for both EXEs copied alone with a
  fresh .NET bundle cache. Temporary virtual MIDI Program Change and multipart
  SysEx passed in both directions, exposing exactly one public MIDI 1.0 port pair.

## FM9 acceptance setup

The development PC at `192.168.2.10` ran the packaged client using its normal
automatic connection setting and an isolated settings directory. The packaged
server ran on Windows 11 workstation `192.168.2.155`, connected to the FM9 over
USB, firmware 12.00. Both used Windows MIDI Services.

The intended arrangement has one FM9-Edit, on the development PC, using the
client's public `FM9 Forwarder Test` ports alongside Preset Maestro. The
workstation's direct FM9-Edit was closed before the final acceptance runs.
Earlier runs with both editors open are recorded separately below.

Preset Maestro 1.2.31's production sync command was exercised through an isolated
headless window/profile. Its MIDI provider remained 0.3.11, so this test isolates
the fix to the Forwarder update. The read-only harness permits identity, current
state, live status, preset-name and stored-preset queries only; it refuses preset
selection, edits and stores. Test evidence is private and ignored under
`artifacts/fm9-0.3.12/`; automated results are under `artifacts/tests/midi-0.3.12/`.

## FM9 acceptance results: one editor through the forwarder

| Production application sync | Slots | Elapsed | Reply timeouts | Retries | Failed presets |
| --- | ---: | ---: | ---: | ---: | ---: |
| Final scan, with editor requests captured | 512 | 138.745 s | 0 | 0 | 0 |
| Repeat after the user exercised amp/effect blocks | 512 | 138.816 s | 0 | 0 | 0 |

Both runs contained 254 populated and 258 empty slots. Each published a complete
library through the real sync command, with exactly 766 scan exchanges (512 name
queries and 254 stored-preset reads). Maximum individual reply waits were
524.289 ms and 523.435 ms respectively. There were no input queue drops, lost
sync-log records or background MIDI failures. Every committed preset record
matched the earlier complete reads, including names, scenes and content hashes.
The active preset and scene remained unchanged before and after both runs.

A read-only observer of the client's relay endpoint captured 163,598 UMPs,
forming 41,564 complete SysEx messages, with no lost records, invalid Fractal
checksums, orphan fragments, abandoned messages or pending fragments at stop.
During the first final scan it saw 721 editor/status `0x01` requests as well as
the 254 stored-preset reads. This confirms additional editor requests overlapped
the scan; editor connection status alone was not used as that evidence. Server
traffic logs also confirm additional requests during the repeat scan.

A fresh 512-name read with the packaged client and editor traffic took 7.989
seconds without a timeout or retry. Four earlier consecutive names-only runs
after the remote editor was closed also completed in approximately eight seconds
each, without timeouts or retries; those four used the production relay service
in a diagnostic capture host rather than the packaged client.

An earlier single-editor scan completed all 512 slots in 142.827 seconds, without
timeouts, retries or failed presets. Its separate selection-invariance assertion
failed because scene 0 became scene 1 during that run. It is retained as a
successful data read, not as a passed selection-invariance test. The user was
then asked to keep the selection unchanged for the two final runs above.

## Earlier two-editor stress runs

Before the remote editor was closed, full application scans completed in
154.963 and 155.091 seconds with no timeout, retry or failed preset. The second
followed a server restart and automatic client reconnection. Both retained the
active preset/scene and produced identical libraries.

This extra-editor arrangement was not uniformly clean: a later names-only scan
needed one recovered timeout at slot 504 and took 11.032 seconds. Other names
reads took approximately eight seconds without retries. The final acceptance
claim above is for the intended single-editor arrangement; it does not claim
every possible multi-application workload is free of timeouts.

## Installed development builds

The tested client is installed at `C:\bin\MidiForwarder.Client.exe` on the
development PC, and the tested server at `C:\bin\MidiForwarder.Server.exe` on
`192.168.2.155`. Each reports product version `1.0.6`, file version `1.0.6.0`.
The previous files were retained alongside them with a `.before-1.0.6` suffix.
Both applications remain connected using isolated test settings; original
startup preferences were not changed. Temporary diagnostic capture processes
have stopped. No preset edits, swaps or stores were sent by the test harness.

These tests do not qualify clean Windows installations, Windows 10, macOS, MIDI
2.0 hardware or preset-write operations.
